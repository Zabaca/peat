# How Peat relates to Neon

**Peat is a fork of [Neon](https://github.com/neondatabase/neon)'s open-source code**: Neon's storage for Postgres (pageserver, safekeepers, storage broker, storage controller) and the Postgres extension its computes run, kept running on the latest PostgreSQL release. It is forked from Neon's code as the community fork [`jclab-oss/neon`](https://github.com/jclab-oss/neon) carries it, at that fork's pull request 14 (`ae51d78b121`), which sits on the community fork's `main` (`4f53557c4f6`: its author's seven commits on Neon's own `main`, `fa504217c61` of 2026-08-31); its Postgres tree is forked from Neon's [`neondatabase/postgres`](https://github.com/neondatabase/postgres) at `REL_18_STABLE_neon` (`a616eefea76`). Neon's code is under the Apache License 2.0 and its Postgres trees under the PostgreSQL licence; Peat's changes are under the same licences. **Peat is not affiliated with or endorsed by Neon or Databricks**; "Neon" is their name, and the code it names below is theirs.

**Why it exists:** Neon's open repository stopped taking new PostgreSQL releases in 2025 (its newest vendored Postgres is 17.5, from July 2025). Neon's own Postgres repository went further, with `REL_17_STABLE_neon` at 17.8 and `REL_18_STABLE_neon` at 18.2 (both last changed in April 2026), but Neon's code never took them in; the community fork did (its pull requests 11 and 14), and Peat carries that work on to **Postgres 18.7**, and to **Postgres 19.0**, which is now its default (18 is still supported and tested), and is meant to follow later releases. It is young but deployed: Zabaca runs it in production for its own databases (its data lake and an internal store, on a Kubernetes cluster, since 2026-11-20; the lake moved to Postgres 19 on 2026-11-25, and by 2026-11-26 all of Zabaca's databases on Peat run on 19, and so does the storage controller's own Postgres, a separate Postgres beside Peat). Its own changes are listed below.

**Who maintains and writes it.** Peat is maintained by Zabaca. Its changes are written by AI coding agents (Anthropic's Claude) working for Zabaca; each change is reviewed by a separate reviewing agent before it is merged, and Zabaca's founder, whose git identity the commits carry, decides the project's direction. Every commit of Peat's own says so in a `Co-Authored-By: Claude` trailer. That matters most for its changes to Postgres internals: the three fixes below are small C changes to PostgreSQL's B-tree search, WAL redo helpers and WAL reader, each listed with what was and was not tested.

**Two repositories:** this one (Neon's tree) and [`peat-postgres`](https://github.com/Zabaca/peat-postgres) (Neon's fork of PostgreSQL, with Peat's 18.7 move on branch `REL_18_STABLE_peat` and its 19.0 port on `REL_19_STABLE_peat`), which `vendor/postgres-v18` and `vendor/postgres-v19` point at.

Neon's own README, with its build and local-run instructions, is kept as [NEON-README.md](NEON-README.md); everything in it applies to Peat, with Peat's Postgres 19 (and 18, which is still supported) in place of Neon's 17.

## What Peat changed

**In the Postgres 18 tree** (`peat-postgres`, branch `REL_18_STABLE_peat`):

1. `f01e2df068f` **Merge PostgreSQL 18.7 into Neon's 18 branch.** 806 upstream commits (18.3 to 18.7). Ten files collided in 22 places; each was resolved keeping Neon's own WAL record formats. The one notable choice: 18.7 registers the visibility-map page in heap WAL records (upstream `f581fa729d8`); Neon writes its own heap records (`RM_NEON_ID`) whose format is unchanged here, so that registration is left out of them, and the pageserver keeps clearing visibility-map bits itself, as it did on 18.2.
2. `a9fd4c1bd18` **nbtree: pass Neon's parent argument in 18.7's new empty-index retry.** A build failure: 18.7 calls `_bt_get_endpoint()` with three arguments where Neon's tree has four. *Tested:* the build and Neon's regression suite on 18.7, which includes the upstream pg_regress and isolation suites. *Not tested:* the race this path exists for; no test reaches it yet (below).
3. `35611b70bb7` **xlogutils: skip the init-fork flush in Neon's WAL redo process.** 18.7 flushes an unlogged sequence's init fork during redo; Neon's WAL redo process has nowhere to flush it to and died, so basebackups failed. *Tested:* `test_unlogged` and the four `test_pg_regress` variants failed before it and pass after it; `test_unlogged_init_fork_on_replica` (added by Peat) checks that a read replica replays an unlogged relation's init fork and keeps serving: it passed on 17.8 and **failed on 18.7**, a second defect, fixed in this repository (below).
4. `9b226aa9479` **xlogreader: forget the queued error of a check skipped on request.** `pg_waldump --ignore` stopped after one record on a safekeeper's WAL segment. The defect was already in Neon's 18.2 tree; 18.7's WAL layout exposed it. *Tested:* `test_pg_waldump` failed before it and passes after it (the skipped page checks); `test_pg_waldump_ignore_skips_corrupt_record` (added by Peat) flips a byte inside a record of a copied WAL segment and checks that `pg_waldump --ignore` still lists every record after it (the skipped-record path); it fails on Neon's 17.8 tree, which lacks this fix. After a skipped record, `--ignore` resumes at the next page, so the rest of that page is not listed: Neon's behaviour, unchanged here.

Each commit message says what it fixes and how it was found.

**In this repository:** `vendor/postgres-v18` points at the tree above (its URL is the relative `../peat-postgres.git`, the way upstream Neon points at its own postgres repository), `vendor/revisions.json` says 18.7, Neon's storage manager lets a read replica replay an unlogged relation's init fork on 18 (`pgxn/neon/pagestore_smgr.c`, below), the CI workflows are set for GitHub's hosted runners (`.github/workflows/peat-ci.yml`), and this README (Neon's is kept as `NEON-README.md`). Nothing else on the Neon side was needed for 18.7. Since then: **Peat's default Postgres version is 19 where Neon's is 17** (it was 18 from 2026-11-18 to 2026-11-26; 18 stays fully supported). The default is what a timeline created without a version gets (the pageserver's `DEFAULT_PG_VERSION`), what `neon_local` creates when not told otherwise (its `--pg-version` defaults), the version of the local storage controller's own database (16 in Neon), and the test suite's default version (`PgVersion.DEFAULT`, the one the tests Neon marks `run_only_on_default_postgres` run on). **A caller that omits `pg_version` now gets a 19 timeline, where it got 18 before 2026-11-26; a caller that wants 18 must say so.** The walproposer library is built against 18 whatever the default is (one guarded signature in `pgxn/neon/walproposer_compat.c`); it only feeds the safekeeper's simulation tests. **An API change:** creating a timeline from another timeline's initdb (`existing_initdb_timeline_id`) now requires `pg_version`, and the pageserver answers 400 without it (Neon takes its default); the storage controller, which does this itself for a sharded timeline's shards above 0, passes shard 0's version. **Upgrade order:** the storage controller before the pageservers, or callers that always pass `pg_version`. An older controller (`3b47cb128` or earlier) with newer pageservers and a caller that omits the version gets the 400 on shards above 0, leaving a sharded timeline half-made until the controller is upgraded.

**In the storage controller** (`storage_controller/src/service/safekeeper_reconciler.rs`): moving a timeline off a safekeeper that is Paused or Decomissioned (a lost log node) used to panic the whole controller, because the request to delete the timeline's copy there was handed to a reconciler that does not exist for such a safekeeper. Now the request is skipped with a warning; the operation stays in the database and is scheduled again when that safekeeper is set Active, or at the next controller start. Such an exclusion is dropped, row included, if the safekeeper is a member of the timeline again (in its set or in the set it is moving to), both when loaded and just before it runs, so a stale one cannot delete a re-added member's copy. *Found:* in the Peat lab (stage 2), the controller panicked at `safekeeper_reconciler.rs:69` while a job replaced a lost safekeeper. *Tested:* unit tests of the skip, of planning again from the persisted rows, of dropping a stale exclusion (current set and target set) and of the per-safekeeper filter; the panic test failed on the code before the change and each of the stale-exclusion tests fails without the check. *Not tested:* the decision in a running controller (the check just before the delete, and the scheduling on Active); there is a small window between that check and the delete in which a migration can add the safekeeper back.

**In the storage controller's records** (`storage_controller/src/persistence/`, `storage_controller/kubernetes/`): the controller can keep its records (generations, pageservers, safekeepers, timelines' safekeeper membership, the leader) in Kubernetes objects instead of a Postgres of its own, with `--records kubernetes`; Postgres stays the default. Each tenant's shards are one object and every write is a compare-and-swap on it, so each change to a tenant's generations is atomic, as it is in one Postgres transaction. Every object carries a revision of the controller's own; a copy of every record goes to a bucket within a second of each change (`--records-copy-storage`, required outside `--dev`), with a mark written before each delete; and every start, and every read while running, compares the records with the copy and the marks, so a cluster whose store (etcd) was taken back or lost objects is refused rather than handing out a generation twice. `storcon_records`, in the storage image, moves records between the two stores and rebuilds them from the copy, every generation raised above anything the copy or the pageservers' store shows. *Tested:* every operation runs the same way on both stores, against a real Kubernetes API server and a Postgres, and the two must agree; attaches of one shard at once, from two controllers, never share a generation; every row of the start's table; an etcd restore under a running controller, for real, with and without `--bump-revision`: the controller records it and exits, and the next start refuses; the copy tool both ways, field by field; a restore after every object was lost. *Not yet:* Neon's controller suites run on the Kubernetes store, and the scale measure ([`storage_controller/kubernetes/README.md`](storage_controller/kubernetes/README.md)).

**In the pageserver's gc-compaction** (`pageserver/src/tenant/timeline/compaction.rs`), two changes taken from patches 0001 and 0003 of [`matisiekpl/neond`](https://github.com/matisiekpl/neond) (Apache License 2.0; `NOTICE` credits them): a sub-compaction job that L0 compaction preempts is queued again (up to three attempts) instead of being counted as done, and a meta job with a failed or given-up job does not advance `l2_lsn`; and a key's history below its latest base image at or below the lowest LSN anything reads is dropped as gc-compaction collects it, so a hot key no longer fails the job at 512 MiB. Neon's `main` has not changed that file since 2025-07-29, so there is no upstream fix. *Found:* by the neond project on its own deployment (about 31 GB of layers for 2 GB of data; every attempt failing on a hot key); neither has been seen on Peat, whose lake is far below the 5 GB at which automatic gc-compaction starts. *Tested:* unit tests of the queue (a preempted job is queued again and the second run compacts; a job preempted three times is given up), which fail on the code before the change; patch 0003's own tests of the accumulator and of compaction after a rebase below the retain LSN; and `test_pageserver_gc_compaction_preempt`, which now also asserts the re-queue, on both architectures. *Not tested:* a key reaching the 512 MiB limit; either defect on real data (Zabaca's own lake is far below the size at which automatic gc-compaction starts).

Files Peat changed are the ones in the commits listed here; `git log fa504217c61..` shows every change since Neon's `main` (the community fork's and Peat's), and `git log ae51d78b121..` Peat's alone. Peat also replaced Neon's process files that would misdirect a contributor here (`CONTRIBUTING.md`, the pull request template; `CODEOWNERS`, the issue templates and the CI helpers of the removed workflows deleted) and trimmed Neon's README (`NEON-README.md`).

## A known defect, found and corrected before publishing

The first repair of the build failure (item 2 above, in its first form) passed `NULL` for Neon's parent argument. That compiled and passed the test suite, but left the scan's `parent` variable without a value on 18.7's new path: under `SERIALIZABLE` isolation, an index-only scan with no usable keys on an empty B-tree index that races the index's first insert could start its prefetch from an arbitrary block number. Review found it; the published commit (`a9fd4c1bd18`) passes `&parent` and initialises the variable. **No test reaches this path yet; one could be written** by holding a backend inside the race window: with PostgreSQL's injection points (which Neon's build does not enable) or with a debugger, as Neon's suite already does elsewhere. It is a to-do. On the defective code the outcome depended on an uninitialised value, so such a test could not have failed reliably on it; upstream added no test for the race either.

## A defect found after the port, fixed: a read replica and an unlogged relation on 18.7

Found by Peat's replica test before publishing and published as a known defect; fixed in Peat's first pull request.

**What triggered it.** On 18.7 a read replica went down when the primary created or rewrote an unlogged sequence (most `ALTER SEQUENCE` options, `TRUNCATE ... RESTART IDENTITY`), including the sequence behind a `serial` or identity column of an unlogged table, or created a hash index on an unlogged table. Run, by the test, each failing on 18.7 before the fix: `CREATE UNLOGGED SEQUENCE`, `CREATE UNLOGGED TABLE ... (id serial)`, and `CREATE INDEX ... USING hash` on an unlogged table. The replica's startup process stopped with `could not open file "base/N/M_init": No such file or directory` and the replica shut down. Only hot-standby read replicas replay the primary's WAL, so only they were affected; no data was lost on the primary.

**Why.** PostgreSQL 18.7 (upstream `62760571307`) makes sequence redo flush the sequence's init-fork page at once, and the hash index's init-page redo goes through the same helper. On a Neon replica, redo of an init-fork page the replica has not cached gets a zeroed buffer back, and redo's relation creation (opened as permanent) makes no local file. Since Postgres 18, Neon's buffer flush sends every init-fork buffer to the relation as unlogged, that is to a local `_init` file, which did not exist. On 17, the flush opened the relation with unknown persistence, found no local file and took Neon's own write path instead.

**The fix** (`pgxn/neon/pagestore_smgr.c`, `neon_writev`): on 18, an unlogged write to an init fork during recovery, with no local `_init` file, takes the path 17 took. Nothing else changes: the primary, and a replica that has the local file, write it locally as before.

**Tested:** `test_unlogged_init_fork_on_replica` covers an unlogged sequence, an unlogged table's `serial` column and a hash index on an unlogged table, each followed by a replica restart and one more such change replayed after it. On an arm64 Linux machine, release build: before the fix its three cases failed on 18.7 with the error above and passed on 17.8; after it they pass on both. The replica, standby and pg_regress test files (`test_unlogged`, `test_hot_standby`, `test_physical_replication`, `test_physical_and_logical_replicaiton`, `test_replica_promotes`, `test_replica_start`, `test_gin_redo`, `test_pg_regress`: 50 tests) pass on 18.7 and 17.8 with the fix. *Not tested:* identity columns and the other `ALTER SEQUENCE` forms (they reach the same redo). A replica promoted after replaying such a change was tested since: it is a limit Neon already had (next section).

## A known limit, as in Neon: a promoted replica cannot read an unlogged table it replayed

Found by `test_unlogged_serial_on_promoted_replica` (Peat's, pull request 3); **not fixed, and not Peat's**: it fails the same way on Postgres 17.8 and 18.7 from the same build, whether the replica is promoted with `pg_promote()` or by Neon's own `compute_ctl` (`/promote`).

**What it reaches.** An unlogged relation that was created, or given a new file (`TRUNCATE`, `VACUUM FULL`, `REINDEX`), on the primary since the replica last started, when that replica is then promoted in place: a hot standby made primary. In the test, `CREATE UNLOGGED TABLE userial (id serial, v int)` and two inserts on the primary, then the promotion. Unlogged relations the replica's own start already found are not reached (inferred: its base backup carries their files; not run). Run, by the test: the table's creation. Inferred and not run: the rewrites, which make a new file the same way.

**What it does.** Promotion succeeds, and the promoted node serves its logged tables. Reading the unlogged table fails with `could not open file "base/N/M": No such file or directory`. PostgreSQL itself empties every unlogged table at a promotion; what is lost here, beyond that, is **the use of the table after a failover**: it errors instead of being empty, until the promoted compute restarts or the table is recreated. Run, by the test, on both versions and both promotion methods: the `SELECT count(*)` fails; then **the promoted compute, restarted as a primary, reads the table as empty and takes an insert** (a restart takes a fresh base backup, which carries the table's files). Inferred and not run: inserts before the restart fail the same way, and recreating the table also clears it.

**Why** (read from the code, not traced): ending recovery resets every unlogged relation by copying its init fork, from the local data directory, over its main fork. A Neon replica replays an unlogged relation's creation through Neon's storage, which makes no local file, so promotion has nothing to copy, and the reads look for a local main fork that was never made. A compute started afresh does not have this limit: the pageserver sends the init fork's contents as the main fork in its base backup (`test_unlogged`).

**Where it applies.** Only to promoting a hot standby in place. A failover that starts a fresh primary compute on the timeline instead gets a base backup and does not meet it; which of the two a failover does is a choice the control plane makes (Neon's own open code promotes in place, through `compute_ctl`; Peat's control plane is not part of this repository).

The test is a strict expected failure, counted only when the table's own main fork is missing on its first use after the promotion (the read, or the insert after it), and only after the restart has shown the table working again, so a fix, or a change in the limit's shape, fails it. Fixing it is not planned in this piece.

## Postgres 19 (Peat's own work, Peat's default)

**What it is.** PostgreSQL 19.0 (`REL_19_0`, `5c839a2a08b`, 2026-11-16) with Neon's change to Postgres carried onto it: the branch `REL_19_STABLE_peat` of `peat-postgres`, which `vendor/postgres-v19` points at. Neon never ported its Postgres change to 19; the only 19 here is Peat's. **Postgres 19 is Peat's default since 2026-11-26** (a timeline created without a version is 19), after it had been built, tested and published beside 18 and Zabaca's data lake had moved to it (2026-11-25). **Postgres 18 stays fully supported**: the same 18.7 tree, built, tested (the whole suite) and published beside 19, and a timeline that asks for 18 gets it; databases already on 18 stay on 18 until they are copied. A database moves from 18 to 19 by copying it (below), not in place.

**How the Postgres tree was made.** Neon's whole change to Postgres 18 (`REL_18_7` to `REL_18_STABLE_peat`, 153 files, +7,500 and -630 lines, Peat's three fixes included) was applied to `REL_19_0` as one squashed commit: 37 files collided, in 81 hunks, resolved by hand; then the fixes the build and Neon's suite found, as separate commits (`peat-postgres` pull request 1 shows only these, against `REL_19_0`). The notable choices:

- **Heap WAL and the visibility map.** As on 18.7, Neon's own heap records (`RM_NEON_ID`) do not register the visibility map page, and the pageserver keeps clearing the bits itself. 19 sets visibility bits in the prune record (`XLOG_HEAP2_PRUNE_*`), which Neon does not rewrite: the heap page is stamped with that record's LSN whether or not a full-page image is allowed, and redo does the same whenever the record sets visibility bits (Neon's rule, that the page LSN the compute tracks must match the one the WAL redo process gives it, carried to where 19 moved the code).
- **Read streams.** 19's hash-index vacuum reads its bucket pages through a read stream; Neon's own prefetch loop there is dropped (the read stream looks ahead itself).
- **Index-only scan prefetch.** 19's `_bt_search` returns its descent stack only when asked; the scan asks when Neon's leaf-page prefetch will use it.
- **Buffer manager.** Neon's local buffers for the WAL redo process, its storage manager's persistence argument and its test-only eviction GUC are carried onto 19's reworked buffer reads and content locks.
- **The WAL redo process's shared memory.** 19 builds shared memory from every subsystem's registered callbacks; the WAL redo process registers the built-in ones and initializes them from its malloc'd segment, leaving out the LISTEN/NOTIFY queue (its start opens `pg_notify`, which the redo process's bare directory does not have).
- **Settings and tools.** Neon's GUCs moved into 19's `guc_parameters.dat`; `pgbench`'s three Neon options were renumbered after 19's `--continue-on-error`; `pg_waldump`'s `--ignore`, `--file`, `--offset`, `--save-records` and `--load-records` were ported onto 19's archive reader.
- **Dropped:** three generated wait-event files that Neon's 18 branch carries (they are 18's and stale for 19).

**The Neon side** (this repository, pull request 19): `vendor/postgres-v19`; a `PG19` version through `postgres_ffi`, the WAL decoder, the pageserver, `compute_tools`, `control_plane` and the test runner; the 19 changes the pageserver depends on (a 64-bit multixact offset: its own page layout, record, truncate record and members segment names of fifteen hex digits; `pg_control` fields; the logical-decoding-status record; a catalog version); Neon's extension and WAL redo process for 19 (`pgxn/`, each change behind `PG_MAJORVERSION_NUM` so the 18 build is unchanged); the images and CI (below). Found and fixed on the way: a database's relations are now dropped from the `rel_size_v2` keyspace when its directory is dropped (a database moved to another tablespace and back, as 19's own tablespace test does, otherwise met its old entries: a warning while migrating, a failed ingest once migrated; not 19-specific, but 19's regression suite is what reaches it).

**Known issues of 19** (beyond the list below):

- **A plain `SELECT` can ask the pageserver for a visibility map or free space map page on 19; on 18 it asks for none.** 19's pruning on access (`heap_page_prune_opt`) sets a page all-visible and records its free space, which reads the free space map page and pins the visibility map page. In a compute whose safekeepers are all down, a read that needs such a page waits for a pageserver that cannot serve it. Two tests encode the 18 behaviour and are marked as expected failures on 19, each with this cause in its source: `test_subscriber_synchronous_commit` (the `SELECT` on the subscriber hung on a `_fsm` page request, seen in the pageserver's log and the backend's wait event `Neon/PS_ReadIO`) and `test_cancellations` (a paused `exists` failpoint cancels a `SELECT` that does not need one on 18). Neither was fixed or tuned: it is how 19 reads, and what it costs a database is not measured.
- **Zabaca's data lake has run on 19 since 2026-11-25**, and since 2026-11-26 all of Zabaca's databases on Peat do, and so does the storage controller's own Postgres (a separate Postgres beside Peat, not a database on its storage); only stopped copies kept as a way back, and scratch copies, stay on 18; the system run above was on a temporary VM, before any of that. Moving a database from 18 to 19 is a copy (below), not in place: Neon's open code has no major-version upgrade and a timeline's version is fixed when it is made. The lake's own move was this copy.

**Moving a database from 18 to 19** (measured on the VM, one run each): `pg_dump` with 19's own tools from the 18 compute, restored into a new 19 timeline: a pgbench database of 456 MB in 12.6 s (new database up in about 5 s of it), of 1,503 MB in 19.6 s; its branch, copied as a database of its own, 9.8 s and 17.3 s. Every table's count and a checksum of its contents were equal before and after. **What the move does to history and branches:** the new database's history starts at the end of the copy; the old LSNs mean nothing on it (a branch of it at one of the old numbers is accepted, and holds whatever the new timeline held at that number); a branch becomes a separate database and no longer shares storage with its parent. Restore points have to be taken again. Not tried: `pg_upgrade` of a base backup followed by Neon's timeline import, which could be faster for databases of tens of gigabytes.


## Known issues

- **`existing_initdb_timeline_id` and the version, the narrower fix.** The pageserver now refuses that request without `pg_version` (above). The fuller fix would read the version from the initdb archive itself (its `PG_VERSION`), so a caller could not state the wrong one; not done. The test of the controller's side (`test_existing_initdb_needs_pg_version`) runs with one pageserver, so it does not reach the controller's branch for stale shard-zero locations, which passes the version the same way.
- **walredo's redo path has no unit test on 18.** The pageserver's two short walredo tests replay WAL records and compare a page that were made on Postgres 14. Run against 18's redo process (once, on a maintainer's temporary VM, with the tests switched to 18 for that run; a transcript is kept in the maintainers' records, not in this repository), it refuses them (`FATAL: failed to decode WAL record: out-of-order block_id 0 at 0/16A9388`), so they are left out of the CI until records and an expected page are made on 18. Its ping and stderr tests run on 18. Redo on 18 is exercised end to end by the regression suite: every page whose WAL includes a Postgres record goes through the redo process (records the pageserver applies itself, Neon's own records such as clearing visibility-map bits, never reach it), under the upstream pg_regress and isolation suites and most of Neon's tests; what is missing is a unit test of the redo request itself.
- **The safekeeper simulation does not test WAL format.** Its tests run walproposer's consensus protocol against simulated safekeepers under faults, over WAL generated and decoded with Postgres 16's format (`postgres_ffi::v16`), whatever version walproposer is built against (18 in Peat). They never tested the WAL format; an 18 walproposer with 18 WAL is covered by the regression suite only.
- **Slow pageserver shutdown on GitHub's hosted runners.** On the 4-CPU runners a pageserver's shutdown is sometimes slower than the suite allows: it logs `Timed out flushing deletion queue on shutdown` (the pageserver gives that flush a hard-coded 5 seconds; allowed in the suite's log check since pull request 2), and some teardowns fail with "N out of M pageservers failed to stop gracefully". Seen in teardowns of `test_image_layer_compression`, `test_tx_abort_with_many_relations`, `test_pg_regress`, `test_scrubber_physical_gc_ancestors[2]`, `test_slow_secondary_downloads`, `test_truncate` and `test_image_consistent_lsn`; not seen on the 16-vCPU VMs. Tracked here as one item, rather than allowed piece by piece: the next step is to measure shutdown times on the runners, before allowing any more of it.
- **`test_storage_controller_smoke[...nnnnn]` probably depends on the scheduler's tie-break by utilization (inferred, not shown).** It expects 4 shards on each of three pageservers. The scheduler ranks nodes by availability zone, then affinity, then each pageserver's reported utilization (`storage_controller/src/scheduler.rs`), and in a failed run's controller log the 12 shards landed 4, 3 and 5 across the nodes, so placement can vary with timing on a slow runner. It failed twice in a row on amd64 in two of the three main runs of 2026-11-19, and passed on rerun; it is not tied to the safekeeper code. Not fixed: a fix in the test would change what it asserts. `test_re_attach_with_stuck_secondary` had the same kind of cause (shown, not inferred) and is fixed: it now runs with two availability zones, and in 30 runs each on a hosted runner the old form failed 9 times on amd64 and 10 on arm64, the new form never.

## Continuous integration

All of it runs on GitHub's standard hosted runners, free for public repositories, each architecture on its own native runner and never emulated (arm64: `ubuntu-24.04-arm`; amd64: `ubuntu-24.04`; both 4 vCPU and 16 GB of memory; GitHub's page states 14 GB of disk, and the runners Peat has had so far have a 145 GB root filesystem with over 100 GB free); no job needs a machine of the maintainers'. Every job that builds or tests is a pair, arm64 and amd64, judged by the same rule: the same expected failures and skips, no new failure. One architecture failing does not cancel the other's jobs, but the regression shards of both start only when both builds have finished. The workflow is `.github/workflows/peat-ci.yml`, its helpers are in `.github/peat/`.

- **Every pull request and every push to `main`:** the release build and Neon's Rust tests, on arm64 and on amd64. Peat builds Postgres 18 and 19 in full, the walproposer library that the safekeeper's simulation tests link included (against 18; Neon builds that against 17), and the headers of 14 to 17, from which the Rust bindings are generated. Fourteen Rust tests that run 14's to 17's programs are left out: WAL crafting for those versions, and the two short walredo tests (Known issues). The Postgres build is cached by the commits of its trees, the build rules, the runner image, the machine architecture, the C compiler and the build type, and the Rust dependencies' build by Swatinem/rust-cache, which puts the runner's architecture into its key (`-Linux-arm64`, `-Linux-x64`); so each architecture has its own caches. Caches are written only from pushes to `main`, so a pull request's run restores them but never writes one that `main` restores.
- **The control folder, every run:** `control/`'s tests, typecheck and public-names check (the job `control`), and the install test: a whole platform installed from the install file and one Platform on a throwaway kind cluster, a database made, written and read back with `verify-full`, slept and woken, the admission rules judged by the cluster's API server (`.github/peat/install-test.sh`; on a pull request with this change's control image and the newest published images of `main`, on `main` with that run's own images). The publish job needs both.
- **Every merge to `main`, every `release-*` tag and manual runs:** also, on each architecture, Neon's Python regression suite on Postgres 18 and on Postgres 19 (nine more jobs per architecture; a failed 19 shard on either holds the publish job, as an 18 one does; the tests Neon marks to run only on the default Postgres run on 19 and are skipped on 18), split by `.github/peat/shard.py` into eight shards balanced by measured test times (`.github/peat/test-durations.json`), plus a job of its own for the two tests that each write about 12 GB (`.github/peat/solo-tests.txt`), each shard on its own runner (thirty-six suite jobs in all, nine per architecture and Postgres version) with four test workers and its test output on a filesystem of its own (the pageserver starts evicting, and the test fails its log check, when its filesystem is over 80% full). A failed test is rerun once; a test that fails twice fails its shard, and every rerun, passed or not, is listed in the job's summary and as a warning on the run, with its first attempt's logs kept in the shard's artifact. [CONTRIBUTING.md](CONTRIBUTING.md#reruns) says what a rerun means here.
- **Images** (public: all three packages can be pulled without signing in), for arm64 and amd64, each built and checked on its own native runner on every merge, release tag and manual run (`.github/peat/check-images.sh`), and published only from this repository's own merges to `main` and release tags, after the regression suite passed on both architectures, and only once the `PUBLISH_IMAGES` repository variable is `true`. **Each published tag is one multi-arch image:** an image index naming the arm64 and the amd64 image, so a pull picks the machine's architecture. Both Dockerfiles start from the same Ubuntu 24.04 index, pinned by digest, and each architecture's image is built from its own architecture's binaries:
  - `ghcr.io/zabaca/peat/storage`: the storage broker, storage controller, safekeeper and pageserver, with the part of Postgres 18 and of Postgres 19 the pageserver runs (`initdb`, `postgres`, at `/usr/local/v18` and `/usr/local/v19`), `sh` and `curl`. **It creates Postgres 18 and 19 timelines:** a timeline created without a version is 19, it carries no other version's `initdb`, and asking for another version fails (`check-images.sh` checks that 18 and 19 are the only versions in it).
  - `ghcr.io/zabaca/peat/control`: the control folder's program on Bun (the operator, the control layer, the gateways; the role is the first argument), from `.github/peat/control.Dockerfile`. A new package on the registry starts private: the maintainer makes it public by hand once.
  - `ghcr.io/zabaca/peat/compute-pg18` and `ghcr.io/zabaca/peat/compute-pg19`: Postgres 18 (or 19) with Neon's extension, and `compute_ctl` as the entrypoint. Neon's compute image also carries dozens of third-party extensions, pgbouncer, `local_proxy`, `fast_import`, metrics exporters and debugging tools; this one carries none of them yet.
  - Tags: the full commit hash for a merge to `main`, the tag's name for a release tag (`release-*`). No moving tag such as `latest`. Beside each such tag the two single-architecture images it is made of stay under `<tag>-arm64` and `<tag>-amd64` (the index refers to them by digest); pull the plain tag. The step summary lists the index's digest and each architecture's.
  - Their programs are built with the default features, as Neon builds its release images, not with the `testing` feature the regression suite uses, so an image's pageserver refuses its test-only HTTP API (setting fail points, forcing a checkpoint, marking a tenant broken and others). Fail points themselves are compiled into every build of this code, Neon's release images included (`pageserver --version` says `failpoints: true`), and the safekeeper's and storage controller's endpoints for them, like the `FAILPOINTS` variable, work in any build. More widely: **without JWT auth, the whole management HTTP API of the safekeeper, the storage controller and the pageserver is open to anyone who reaches its port** (on a safekeeper, deleting a tenant; on the controller, its node and tenant operations; fail points are the smaller part). So either their management ports stay off any network a tenant reaches, or JWT auth is on, as with Neon's own images. Postgres's debug information is stripped (function names stay). Both are on Ubuntu 24.04, pinned by digest, the system the runners build on.
  - The compute image leaves out Neon's test extension `neon_test_utils`: it is marked trusted, so a database owner could create it and crash or stall the compute (`trigger_panic`, `test_consume_memory` and others). The regression suite's build keeps it. `check-images.sh` checks it is absent.
  - **Who can publish:** the publish job pushes only the images the images jobs checked (each architecture's four images have their IDs compared after loading, and the job fails unless all eight match), makes the multi-arch tag only from the digests it has just pushed, checks the index before it is created (a dry run: exactly two images, linux/arm64 and linux/amd64, the pushed digests, nothing else) and again after, creates a call's tags only after that call's architecture images are pushed (`storage` and `compute-pg18` in one call, exactly as before the 19 port, then `compute-pg19` and `control` in calls of their own), never overwrites an existing tag with different images (a rerun of the whole workflow rebuilds the images, so it fails there: rerun only the failed job; the same images again are left alone), and refuses a commit that is not on `main`; the digests it published are in its step summary. The script has its own test against a throwaway registry (`.github/peat/test-push-images.sh`, the job `test the publish script`, which the publish job needs, as it needs the `control` job and the install test). The repository's rulesets let `main` change only through a pull request (no force push, no deletion; nobody bypasses), and let only repository admins create a `release-*` tag, which nobody may move or delete. Repository admins and organisation owners can still edit or disable a ruleset. **A pull request needs no approval and no passing check to merge**, so anyone with write access (today the one maintainer) can merge, and so publish, an unreviewed change; adding a collaborator is the moment to require an approval and the CI's checks.
  - **A tag that is half published, or was refused:** the script puts nothing under a tag until its call's architecture images are pushed and its indexes pass their checks (`compute-pg19`'s call runs after the first, so a stop between them leaves 18's images published and 19's compute not), so a stop before that leaves only `<tag>-arm64` and `<tag>-amd64` tags, which a rerun overwrites. If it stopped between the two indexes (storage's is made, compute's is not), run "Re-run failed jobs" on the workflow run (not "Re-run all jobs") within seven days, while the checked images are still kept as artifacts: the script leaves the published index and finishes the other. "Re-run all jobs" rebuilds the images with new IDs, so the script refuses it with `exists with a different linux/... image`, and nothing is pushed. To replace a published tag on purpose (a wrong image went out, say), a maintainer deletes that tag's package version, for `storage`, `compute-pg18` and `compute-pg19`, in the package's settings page on GitHub (Packages, then the package, then the version), then reruns only the publish job of the run that holds the images to publish. Deleting a version by hand is irreversible and anyone pulling it by digest loses it; nothing in the workflow deletes one.

Neon's upstream workflows were removed: they need Neon's own infrastructure (self-hosted runner labels, AWS and Azure accounts, Neon's cloud, a private test-data bucket), and two of them ran on `pull_request_target`. They remain in the history.

**For contributors:** pull requests from other repositories run on GitHub's machines with a read-only token and no secrets; the workflow token has no permission unless a job asks for one, and only the image job, which never runs for a pull request, can write. The workflow runs of every pull request from outside wait for a maintainer's approval before they start (a repository setting).

**Known external dependency:** Neon's proxy tests resolve names under `local.neon.build`, a public DNS name of Neon's that points at `127.0.0.1`; without DNS (or if that name goes away) those tests fail.
