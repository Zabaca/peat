# Peat

**Peat is a fork of [Neon](https://github.com/neondatabase/neon)'s open-source code**: Neon's storage for Postgres (pageserver, safekeepers, storage broker, storage controller) and the Postgres extension its computes run, kept running on the latest PostgreSQL release. It is forked from Neon's code as the community fork [`jclab-oss/neon`](https://github.com/jclab-oss/neon) carries it, at that fork's pull request 14 (`ae51d78b121`), which sits on the community fork's `main` (`4f53557c4f6`: its author's seven commits on Neon's own `main`, `fa504217c61` of 2026-08-31); its Postgres tree is forked from Neon's [`neondatabase/postgres`](https://github.com/neondatabase/postgres) at `REL_18_STABLE_neon` (`a616eefea76`). Neon's code is under the Apache License 2.0 and its Postgres trees under the PostgreSQL licence; Peat's changes are under the same licences. **Peat is not affiliated with or endorsed by Neon or Databricks**; "Neon" is their name, and the code it names below is theirs.

**Why it exists:** Neon's open repository stopped taking new PostgreSQL releases in 2025 (its newest vendored Postgres is 17.5, from July 2025). Neon's own Postgres repository went further, with `REL_17_STABLE_neon` at 17.8 and `REL_18_STABLE_neon` at 18.2 (both last changed in April 2026), but Neon's code never took them in; the community fork did (its pull requests 11 and 14), and Peat carries that work on to **Postgres 18.7** and is meant to follow later releases. It is new: nothing in it has run in production or as a deployed system, and its own changes are listed below.

**Who maintains and writes it.** Peat is maintained by Zabaca. Its changes are written by AI coding agents (Anthropic's Claude) working for Zabaca; each change is reviewed by a separate reviewing agent before it is merged, and Zabaca's founder, whose git identity the commits carry, decides the project's direction. Every commit of Peat's own says so in a `Co-Authored-By: Claude` trailer. That matters most for its changes to Postgres internals: the three fixes below are small C changes to PostgreSQL's B-tree search, WAL redo helpers and WAL reader, each listed with what was and was not tested.

**Two repositories:** this one (Neon's tree) and [`peat-postgres`](https://github.com/Zabaca/peat-postgres) (Neon's fork of PostgreSQL, with Peat's 18.7 move on branch `REL_18_STABLE_peat`), which `vendor/postgres-v18` points at.

Neon's own README, with its build and local-run instructions, is kept as [NEON-README.md](NEON-README.md); everything in it applies to Peat, with Peat's Postgres 18 in place of Neon's.

## What Peat changed

**In the Postgres 18 tree** (`peat-postgres`, branch `REL_18_STABLE_peat`):

1. `f01e2df068f` **Merge PostgreSQL 18.7 into Neon's 18 branch.** 806 upstream commits (18.3 to 18.7). Ten files collided in 22 places; each was resolved keeping Neon's own WAL record formats. The one notable choice: 18.7 registers the visibility-map page in heap WAL records (upstream `f581fa729d8`); Neon writes its own heap records (`RM_NEON_ID`) whose format is unchanged here, so that registration is left out of them, and the pageserver keeps clearing visibility-map bits itself, as it did on 18.2.
2. `a9fd4c1bd18` **nbtree: pass Neon's parent argument in 18.7's new empty-index retry.** A build failure: 18.7 calls `_bt_get_endpoint()` with three arguments where Neon's tree has four. *Tested:* the build and Neon's regression suite on 18.7, which includes the upstream pg_regress and isolation suites. *Not tested:* the race this path exists for; no test reaches it yet (below).
3. `35611b70bb7` **xlogutils: skip the init-fork flush in Neon's WAL redo process.** 18.7 flushes an unlogged sequence's init fork during redo; Neon's WAL redo process has nowhere to flush it to and died, so basebackups failed. *Tested:* `test_unlogged` and the four `test_pg_regress` variants failed before it and pass after it; `test_unlogged_init_fork_on_replica` (added by Peat) checks that a read replica replays an unlogged relation's init fork and keeps serving: it passed on 17.8 and **failed on 18.7**, a second defect, fixed in this repository (below).
4. `9b226aa9479` **xlogreader: forget the queued error of a check skipped on request.** `pg_waldump --ignore` stopped after one record on a safekeeper's WAL segment. The defect was already in Neon's 18.2 tree; 18.7's WAL layout exposed it. *Tested:* `test_pg_waldump` failed before it and passes after it (the skipped page checks); `test_pg_waldump_ignore_skips_corrupt_record` (added by Peat) flips a byte inside a record of a copied WAL segment and checks that `pg_waldump --ignore` still lists every record after it (the skipped-record path); it fails on Neon's 17.8 tree, which lacks this fix. After a skipped record, `--ignore` resumes at the next page, so the rest of that page is not listed: Neon's behaviour, unchanged here.

Each commit message says what it fixes and how it was found.

**In this repository:** `vendor/postgres-v18` points at the tree above (its URL is the relative `../peat-postgres.git`, the way upstream Neon points at its own postgres repository), `vendor/revisions.json` says 18.7, Neon's storage manager lets a read replica replay an unlogged relation's init fork on 18 (`pgxn/neon/pagestore_smgr.c`, below), the CI workflows are set for GitHub's hosted runners (`.github/workflows/peat-ci.yml`), and this README (Neon's is kept as `NEON-README.md`). Nothing else on the Neon side was needed for 18.7. Since then, for building 18 only: **Peat's default Postgres version is 18 where Neon's is 17** (a timeline created without a version: the pageserver's `DEFAULT_PG_VERSION`; `neon_local`'s defaults; the local storage controller's database, 16 in Neon), the walproposer library is built against 18 (one guarded signature in `pgxn/neon/walproposer_compat.c`), and the test suite's default version is 18. **An API change:** creating a timeline from another timeline's initdb (`existing_initdb_timeline_id`) now requires `pg_version`, and the pageserver answers 400 without it (Neon takes its default); the storage controller, which does this itself for a sharded timeline's shards above 0, passes shard 0's version. **Upgrade order:** the storage controller before the pageservers, or callers that always pass `pg_version`. An older controller (`3b47cb128` or earlier) with newer pageservers and a caller that omits the version gets the 400 on shards above 0, leaving a sharded timeline half-made until the controller is upgraded.

Files Peat changed are the ones in the commits listed here; `git log fa504217c61..` shows every change since Neon's `main` (the community fork's and Peat's), and `git log ae51d78b121..` Peat's alone. Peat also replaced Neon's process files that would misdirect a contributor here (`CONTRIBUTING.md`, the pull request template; `CODEOWNERS`, the issue templates and the CI helpers of the removed workflows deleted) and trimmed Neon's README (`NEON-README.md`).

## A known defect, found and corrected before publishing

The first repair of the build failure (item 2 above, in its first form) passed `NULL` for Neon's parent argument. That compiled and passed the test suite, but left the scan's `parent` variable without a value on 18.7's new path: under `SERIALIZABLE` isolation, an index-only scan with no usable keys on an empty B-tree index that races the index's first insert could start its prefetch from an arbitrary block number. Review found it; the published commit (`a9fd4c1bd18`) passes `&parent` and initialises the variable. **No test reaches this path yet; one could be written** by holding a backend inside the race window: with PostgreSQL's injection points (which Neon's build does not enable) or with a debugger, as Neon's suite already does elsewhere. It is a to-do. On the defective code the outcome depended on an uninitialised value, so such a test could not have failed reliably on it; upstream added no test for the race either.

## A defect found after the port, fixed: a read replica and an unlogged relation on 18.7

Found by Peat's replica test before publishing and published as a known defect; fixed in Peat's first pull request.

**What triggered it.** On 18.7 a read replica went down when the primary created or rewrote an unlogged sequence (most `ALTER SEQUENCE` options, `TRUNCATE ... RESTART IDENTITY`), including the sequence behind a `serial` or identity column of an unlogged table, or created a hash index on an unlogged table. Run, by the test, each failing on 18.7 before the fix: `CREATE UNLOGGED SEQUENCE`, `CREATE UNLOGGED TABLE ... (id serial)`, and `CREATE INDEX ... USING hash` on an unlogged table. The replica's startup process stopped with `could not open file "base/N/M_init": No such file or directory` and the replica shut down. Only hot-standby read replicas replay the primary's WAL, so only they were affected; no data was lost on the primary.

**Why.** PostgreSQL 18.7 (upstream `62760571307`) makes sequence redo flush the sequence's init-fork page at once, and the hash index's init-page redo goes through the same helper. On a Neon replica, redo of an init-fork page the replica has not cached gets a zeroed buffer back, and redo's relation creation (opened as permanent) makes no local file. Since Postgres 18, Neon's buffer flush sends every init-fork buffer to the relation as unlogged, that is to a local `_init` file, which did not exist. On 17, the flush opened the relation with unknown persistence, found no local file and took Neon's own write path instead.

**The fix** (`pgxn/neon/pagestore_smgr.c`, `neon_writev`): on 18, an unlogged write to an init fork during recovery, with no local `_init` file, takes the path 17 took. Nothing else changes: the primary, and a replica that has the local file, write it locally as before.

**Tested:** `test_unlogged_init_fork_on_replica` covers an unlogged sequence, an unlogged table's `serial` column and a hash index on an unlogged table, each followed by a replica restart and one more such change replayed after it. On an arm64 Linux machine, release build: before the fix its three cases failed on 18.7 with the error above and passed on 17.8; after it they pass on both. The replica, standby and pg_regress test files (`test_unlogged`, `test_hot_standby`, `test_physical_replication`, `test_physical_and_logical_replicaiton`, `test_replica_promotes`, `test_replica_start`, `test_gin_redo`, `test_pg_regress`: 50 tests) pass on 18.7 and 17.8 with the fix. *Not tested:* identity columns and the other `ALTER SEQUENCE` forms (they reach the same redo). A replica promoted after replaying such a change was tested since: it is a limit Neon already had (next section).

## A known limit, as in Neon: a promoted replica cannot read an unlogged table it replayed

Found by `test_unlogged_serial_on_promoted_replica` (Peat's, pull request 3); **not fixed, and not Peat's**: it fails the same way on Postgres 17.8 and 18.7 from the same build, whether the replica is promoted with `pg_promote()` or by Neon's own `compute_ctl` (`/promote`).

**What it reaches.** An unlogged relation that was created, or given a new file (`TRUNCATE`, `VACUUM FULL`, `REINDEX`), on the primary since the replica last started, when that replica is then promoted in place: a hot standby made primary. In the test, `CREATE UNLOGGED TABLE userial (id serial, v int)` and two inserts on the primary, then the promotion. Unlogged relations the replica's own start already found are not reached (inferred: its base backup carries their files; not run). Run, by the test: the table's creation. Inferred and not run: the rewrites, which make a new file the same way.

**What it does.** Promotion succeeds, and the promoted node serves its logged tables. Reading the unlogged table fails with `could not open file "base/N/M": No such file or directory`. PostgreSQL itself empties every unlogged table at a promotion; what is lost here, beyond that, is **the use of the table after a failover**: it errors instead of being empty, until the promoted compute restarts or the table is recreated. Run, by the test, on both versions and both promotion methods: the `SELECT count(*)` fails; then **the promoted compute, restarted as a primary, reads the table as empty and takes an insert** (a restart takes a fresh base backup, which carries the table's files). Inferred and not run: inserts before the restart fail the same way, and recreating the table also clears it.

**Why** (read from the code, not traced): ending recovery resets every unlogged relation by copying its init fork, from the local data directory, over its main fork. A Neon replica replays an unlogged relation's creation through Neon's storage, which makes no local file, so promotion has nothing to copy, and the reads look for a local main fork that was never made. A compute started afresh does not have this limit: the pageserver sends the init fork's contents as the main fork in its base backup (`test_unlogged`).

**Where it applies.** Only to promoting a hot standby in place. A failover that starts a fresh primary compute on the timeline instead gets a base backup and does not meet it; which of the two a failover does is a choice the control plane makes (Neon's own open code promotes in place, through `compute_ctl`; Peat's control plane is not written yet).

The test is a strict expected failure, counted only when the table's own main fork is missing on its first use after the promotion (the read, or the insert after it), and only after the restart has shown the table working again, so a fix, or a change in the limit's shape, fails it. Fixing it is not planned in this piece.

## Known issues

- **`existing_initdb_timeline_id` and the version, the narrower fix.** The pageserver now refuses that request without `pg_version` (above). The fuller fix would read the version from the initdb archive itself (its `PG_VERSION`), so a caller could not state the wrong one; not done. The test of the controller's side (`test_existing_initdb_needs_pg_version`) runs with one pageserver, so it does not reach the controller's branch for stale shard-zero locations, which passes the version the same way.
- **walredo's redo path has no unit test on 18.** The pageserver's two short walredo tests replay WAL records and compare a page that were made on Postgres 14. Run against 18's redo process (once, on a maintainer's temporary VM, with the tests switched to 18 for that run; a transcript is kept in the maintainers' records, not in this repository), it refuses them (`FATAL: failed to decode WAL record: out-of-order block_id 0 at 0/16A9388`), so they are left out of the CI until records and an expected page are made on 18. Its ping and stderr tests run on 18. Redo on 18 is exercised end to end by the regression suite: every page whose WAL includes a Postgres record goes through the redo process (records the pageserver applies itself, Neon's own records such as clearing visibility-map bits, never reach it), under the upstream pg_regress and isolation suites and most of Neon's tests; what is missing is a unit test of the redo request itself.
- **The safekeeper simulation does not test WAL format.** Its tests run walproposer's consensus protocol against simulated safekeepers under faults, over WAL generated and decoded with Postgres 16's format (`postgres_ffi::v16`), whatever version walproposer is built against (18 in Peat). They never tested the WAL format; an 18 walproposer with 18 WAL is covered by the regression suite only.
- **Slow pageserver shutdown on GitHub's hosted runners.** On the 4-CPU runners a pageserver's shutdown is sometimes slower than the suite allows: it logs `Timed out flushing deletion queue on shutdown` (the pageserver gives that flush a hard-coded 5 seconds; allowed in the suite's log check since pull request 2), and some teardowns fail with "N out of M pageservers failed to stop gracefully". Seen in teardowns of `test_image_layer_compression`, `test_tx_abort_with_many_relations`, `test_pg_regress`, `test_scrubber_physical_gc_ancestors[2]`, `test_slow_secondary_downloads`, `test_truncate` and `test_image_consistent_lsn`; not seen on the 16-vCPU VMs. Tracked here as one item, rather than allowed piece by piece: the next step is to measure shutdown times on the runners, before allowing any more of it.

## Continuous integration

All of it runs on GitHub's standard hosted runners, free for public repositories, each architecture on its own native runner and never emulated (arm64: `ubuntu-24.04-arm`; amd64: `ubuntu-24.04`; both 4 vCPU and 16 GB of memory; GitHub's page states 14 GB of disk, and the runners Peat has had so far have a 145 GB root filesystem with over 100 GB free); no job needs a machine of the maintainers'. Every job that builds or tests is a pair, arm64 and amd64, judged by the same rule: the same expected failures and skips, no new failure. One architecture failing does not cancel the other's jobs, but the regression shards of both start only when both builds have finished. The workflow is `.github/workflows/peat-ci.yml`, its helpers are in `.github/peat/`.

- **Every pull request and every push to `main`:** the release build and Neon's Rust tests, on arm64 and on amd64. Peat builds Postgres 18 only, the walproposer library that the safekeeper's simulation tests link included (Neon builds that against 17), and the headers of 14 to 17, from which the Rust bindings are generated. Fourteen Rust tests that run 14's to 17's programs are left out: WAL crafting for those versions, and the two short walredo tests (Known issues). The Postgres build is cached by the commits of its trees, the build rules, the runner image, the machine architecture, the C compiler and the build type, and the Rust dependencies' build by Swatinem/rust-cache, which puts the runner's architecture into its key (`-Linux-arm64`, `-Linux-x64`); so each architecture has its own caches. Caches are written only from pushes to `main`, so a pull request's run restores them but never writes one that `main` restores.
- **Every merge to `main`, every `release-*` tag and manual runs:** also, on each architecture, Neon's Python regression suite on Postgres 18, split by `.github/peat/shard.py` into eight shards balanced by measured test times (`.github/peat/test-durations.json`), plus a job of its own for the two tests that each write about 12 GB (`.github/peat/solo-tests.txt`), each shard on its own runner (eighteen suite jobs in all, nine per architecture) with four test workers and its test output on a filesystem of its own (the pageserver starts evicting, and the test fails its log check, when its filesystem is over 80% full). A failed test is rerun once; a test that fails twice fails its shard, and every rerun, passed or not, is listed in the job's summary and as a warning on the run, with its first attempt's logs kept in the shard's artifact. [CONTRIBUTING.md](CONTRIBUTING.md#reruns) says what a rerun means here.
- **Images,** for arm64 and amd64, each built and checked on its own native runner on every merge, release tag and manual run (`.github/peat/check-images.sh`), and published only from this repository's own merges to `main` and release tags, after the regression suite passed on both architectures, and only once the `PUBLISH_IMAGES` repository variable is `true`. **Each published tag is one multi-arch image:** an image index naming the arm64 and the amd64 image, so a pull picks the machine's architecture. Both Dockerfiles start from the same Ubuntu 24.04 index, pinned by digest, and each architecture's image is built from its own architecture's binaries:
  - `ghcr.io/zabaca/peat/storage`: the storage broker, storage controller, safekeeper and pageserver, with the part of Postgres 18 the pageserver runs (`initdb`, `postgres`, at `/usr/local/v18`), `sh` and `curl`. **It creates Postgres 18 timelines only:** it carries no other version's `initdb`, a timeline created without a version is 18, and asking for another version fails (`check-images.sh` checks that 18 is the only version in it).
  - `ghcr.io/zabaca/peat/compute-pg18`: Postgres 18 with Neon's extension, and `compute_ctl` as the entrypoint. Neon's compute image also carries dozens of third-party extensions, pgbouncer, `local_proxy`, `fast_import`, metrics exporters and debugging tools; this one carries none of them yet.
  - Tags: the full commit hash for a merge to `main`, the tag's name for a release tag (`release-*`). No moving tag such as `latest`. Beside each such tag the two single-architecture images it is made of stay under `<tag>-arm64` and `<tag>-amd64` (the index refers to them by digest); pull the plain tag. The step summary lists the index's digest and each architecture's.
  - Their programs are built with the default features, as Neon builds its release images, not with the `testing` feature the regression suite uses, so an image's pageserver refuses its test-only HTTP API (setting fail points, forcing a checkpoint, marking a tenant broken and others). Fail points themselves are compiled into every build of this code, Neon's release images included (`pageserver --version` says `failpoints: true`), and the safekeeper's and storage controller's endpoints for them, like the `FAILPOINTS` variable, work in any build. More widely: **without JWT auth, the whole management HTTP API of the safekeeper, the storage controller and the pageserver is open to anyone who reaches its port** (on a safekeeper, deleting a tenant; on the controller, its node and tenant operations; fail points are the smaller part). So either their management ports stay off any network a tenant reaches, or JWT auth is on, as with Neon's own images. Postgres's debug information is stripped (function names stay). Both are on Ubuntu 24.04, pinned by digest, the system the runners build on.
  - The compute image leaves out Neon's test extension `neon_test_utils`: it is marked trusted, so a database owner could create it and crash or stall the compute (`trigger_panic`, `test_consume_memory` and others). The regression suite's build keeps it. `check-images.sh` checks it is absent.
  - **Who can publish:** the publish job pushes only the images the images jobs checked (each architecture's two images have their IDs compared after loading, and the job fails unless all four match), makes the multi-arch tag only from the digests it has just pushed and reads the index back to check it names exactly those two, and refuses a commit that is not on `main`; the digests it pushed are in its step summary. The repository's rulesets let `main` change only through a pull request (no force push, no deletion; nobody bypasses), and let only repository admins create a `release-*` tag, which nobody may move or delete. Repository admins and organisation owners can still edit or disable a ruleset. **A pull request needs no approval and no passing check to merge**, so anyone with write access (today the one maintainer) can merge, and so publish, an unreviewed change; adding a collaborator is the moment to require an approval and the CI's checks.

Neon's upstream workflows were removed: they need Neon's own infrastructure (self-hosted runner labels, AWS and Azure accounts, Neon's cloud, a private test-data bucket), and two of them ran on `pull_request_target`. They remain in the history.

**For contributors:** pull requests from other repositories run on GitHub's machines with a read-only token and no secrets; the workflow token has no permission unless a job asks for one, and only the image job, which never runs for a pull request, can write. The workflow runs of every pull request from outside wait for a maintainer's approval before they start (a repository setting).

**Known external dependency:** Neon's proxy tests resolve names under `local.neon.build`, a public DNS name of Neon's that points at `127.0.0.1`; without DNS (or if that name goes away) those tests fail.
